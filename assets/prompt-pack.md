# 提示词库（复制即用）

按阶段组织。尖括号 `<...>` 处替换为你的内容。

## A. 开局（每个项目一次）

> 通读仓库，产出 `AGENTS.md` 草稿：模块划分与依赖方向、启动/测试/构建命令、代码风格、安全红线、性能预算、已知的坑。不确定的列问题清单问我，不要猜。然后给出 `.env.example` 和一个聚合校验命令 `make check`。

## B. 需求澄清

> 不要写代码。针对 `<需求>`，提出 3–5 个最影响架构的问题，每题附默认建议。再列出你认为本次明确「不做」的范围，以及该方案依赖的全部隐含假设（按返工代价排序）。

> 用 Given/When/Then 把这个需求写成可测的验收标准，包含空值、超长、非法类型、并发重复、权限不足、依赖不可用六类边界。

## C. 方案

> 给 3 个实现方案，表格对比：改动文件清单、性能影响、扩展性影响、安全影响、回滚成本、工时。推荐一个并说明为什么、代价是什么。先不要实现，等我批准。

> 这个需求里，哪些部分应该用现成能力（标准库/框架特性/已有内部模块/成熟依赖）而不是自己写？逐个给出理由，并确认推荐的包真实存在及其维护状态。

## D. 拆分

> 把批准的方案拆成 5–10 个顺序任务，每个任务可单独验证、可单独回滚，并写明验证命令或断言。标出依赖关系与可并行项。

## E. 实现

> 按顺序执行。契约与类型 → 先写会失败的测试并运行给我看失败输出 → 最小实现 → 复跑。完成后运行 `<make check>`，把真实输出贴出来。任何一步失败就继续修，不要回来问我是否现在测试。只改 `<目录>`，需要触碰其他文件先列清单说明理由。不新增依赖。

> 保持公共 API 与现有测试全绿的前提下重构 `<模块>`，拆分为 `<...>`。每步一个提交。不允许修改或放宽现有断言——如果你认为某条断言本身错了，停下来告诉我理由。

> 修这个 bug：命令 `<X>`，输入 `<A>`，期望 `<B>`，实际 `<C>`，堆栈 `<...>`。先写能复现它的失败测试，展示失败输出，再修复并展示通过。修完说明根因，以及同类问题还潜伏在哪几处。

## F. 性能

> 不要提优化建议。先写剖析脚本，跑出 `<接口/流程>` 的当前数据（调用次数、P50/P95、DB 行数、字节），指出前 3 个瓶颈及占比。然后只做能解释这些数据的改动，改完复测给前后对比。逐条回答这份清单：N+1、缺失索引、无分页、无缓存、串行可并行请求、循环内重复计算、主线程阻塞、包体过大。

> 为刚才的优化加一个可复现的性能回归脚本：指标写入文件，超过基线 20% 时以非零码退出，并接入 `<make check>`。

## G. 扩展性

> 未来 6 个月最可能的 3 类变更是 `<...>`。只为这 3 类留扩展点，其余按当前需求最简实现。指出你为每项留了什么、为什么不再多留。

> 列出这次改动的全部影响面：调用方、数据读写、事件消费者、缓存键、权限判断、监控与日志字段、文档。每项说明你如何验证。

> 为 `<schema 变更>` 写迁移：前滚与回滚都可执行，加字段而非改名删列，给出大表回填的分批方案与锁影响评估。

## H. 安全

> 先做威胁建模再写代码：资产与敏感数据、全部外部输入入口（HTTP 参数、上传、消息、数据库读出的内容、第三方回调、用户提供的 URL）、信任边界、每类攻击者能造成的最坏后果、对应控制措施。区分「必须由架构保证」与「代码细节」。

> 逐条回答这些高危项在当前实现里如何防御、用什么测试证明：SQL/命令/模板注入、路径穿越、反射与存储 XSS、CSRF、SSRF、开放重定向、越权（水平/垂直）、会话与令牌、反序列化、依赖已知漏洞、上传、竞态与幂等缺失、日志与错误信息泄漏。

> 切换为攻击者：写出具体的利用请求（含参数），目标是 `<越权读取他人数据 / 绕过认证>`。然后以防御者身份修复，并为每个利用补一个测试，确认修复后测试通过。

> 审计鉴权与授权路径：是否存在任何一条数据访问没有做资源归属校验？默认是拒绝还是放行？新增路由是否会漏掉认证？逐条给文件:行号。

## I. 评审（用新会话或子智能体）

> 以三个独立角色审查这次 diff，各自输出 `文件:行号 | 严重级别 | 影响 | 修复建议`：① 安全评审员；② 性能工程师；③ 六个月后接手 this 代码的工程师（可读性、缺失文档、隐藏耦合、脆弱假设）。只报会影响正确性、安全性、可维护性的问题，风格问题不要报。

> 假设这次改动上线后导致 `<接口 5xx 突增>`，列出 5 个最可能的原因及各自如何用日志/指标在 3 分钟内确认或排除。

## J. UI / 网站

> 启动 dev 服务器，用浏览器打开 `<页面>`：截图 → 读取 console 错误与失败网络请求 → 逐一执行交互路径 `<...>` → 在 360/768/1280/1920 四档视口复截图。有问题继续修。最后把截图与 console 结果作为验收证据。任一环节不过则视为未完成。

> 部署前先给我发布计划：改动文件、数据库迁移、所需密钥、回滚步骤、预览地址。我确认后你再 publish。上线后拉取发布状态与分析数据验证。

## K. 收尾与沉淀

> 生成变更说明：用户视角 what/why、迁移与回滚步骤、运维需准备的配置、验收数据（性能/覆盖率前后对比）、仍需人工真机验证的清单。另外指出本次踩到的、值得写进 `AGENTS.md` 的项目级约定。

> 压缩当前上下文为四段：已定决策 / 当前状态 / 剩余任务 / 阻塞点。作为后续工作的新基线。

## L. 元技巧（三个万能句）

1. **逼出假设**：「在这个方案里，你做了哪些我没有同意的决定？」
2. **禁止口头成功**：「不要用『应该』。要么贴出命令输出，要么明确写『未验证』。」
3. **控制范围**：「现在只回答问题，不要修改任何文件。」
