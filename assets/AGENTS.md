## 3. 架构与目录

```

src/application   编排、事务边界
src/adapter       DB / HTTP / 队列 / 外部服务
src/ui            界面，只依赖 application 暴露的类型
```

依赖方向单向向内。跨层调用需在改动计划中说明理由。

## 4. 技术约定

- 语言/框架版本：<...>；不要为单个任务升级主依赖。
- 新增依赖前必须说明：用途、体积、许可证、维护状态，并确认包真实存在（防幻觉包名）。
- 时间统一 UTC 存储、<格式> 输出；金额用最小单位整数，不用浮点。
- 错误：领域错误用类型化错误，不抛裸字符串；对外不回显堆栈。

## 5. 编码风格

- 默认不写注释；只在「为什么」不显然时写一行（隐藏约束、变通、反直觉不变量）。
- 命名揭示意图；函数不超过 <N> 行，不混抽象层级。
- 不写占位/TODO 式半成品实现；要么做完要么不做。
- 不为假想需求做抽象：重复三次才抽象。

## 6. 安全红线（违反即视为缺陷）

1. 所有路由默认需认证；公开接口显式白名单声明。
2. 每条数据读写做**资源级授权**（校验归属），仅检查「已登录」不合格。
3. 入口用 schema 白名单校验，拒绝未知字段；输出按上下文编码。
4. SQL 只允许参数绑定；禁止字符串拼接 SQL/shell/路径/排序字段。
5. 密钥只来自环境变量/密钥服务；禁止硬编码、禁止写日志、禁止进仓库。
6. 加密/哈希/随机数/签名只用成熟库标准接口；禁止自实现算法、自造 salt/IV。
7. 用户提供的 URL 不得由服务端直接请求（SSRF）；如必须，走白名单与内网地址屏蔽。

## 7. 性能预算（超出即视为缺陷）

```
接口 P95 ≤ <120ms>   首屏 LCP ≤ <1.5s>   包体(gzip) ≤ <180KB>
单请求 DB 查询 ≤ <5> 次   列表必须分页（默认 <50>）   常驻内存 ≤ <...>
```

优化必须有剖析数据支撑；改动前后给数字对比。

## 8. 变更纪律

- 一次一个变更集；功能与重构不混在一起提交。
- 修 bug 先写复现测试（红）再修（绿）。**放宽/修改现有断言必须人工确认。**
- schema 变更走迁移脚本，前滚+回滚都可执行；同一次发布不改名不删列。
- UI 改动必须真实浏览器验证：截图 + console 无错误 + 无失败请求。
- 破坏性操作（删除数据/分支、force push、生产发布、上线）先给计划，得到确认再执行。
