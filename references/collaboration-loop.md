# 01 · 六阶段协作循环

每阶段三列：**你说什么**（可直接抄的话术）、**要拿到的证据**（没拿到就别进下一阶段）、**典型翻车**。

---

## 阶段 0 · 建立基线（每个项目一次，持续修订）

目标：消除「每次会话都要重新解释项目」。

**你说什么**
> 阅读整个仓库，产出 `AGENTS.md` 草稿：模块划分、启动/测试/构建命令、依赖关系、代码风格、禁止事项、验收标准。不确定的地方列出问题清单问我，不要猜。

**证据**：AI 给出的 `AGENTS.md` + 一份「我不确定」问题清单。新人（或另一个 AI 会话）只读该文件能否跑起来并做第一个改动。

**翻车**：把 AI 的自我介绍当成文档照收，不加人工校正 → 基线里全是幻觉。

顺带固化：`.env.example`、`make dev` / `npm run check` 一键命令、格式化与 lint 配置、CI。
> 一键可运行 = AI 可自主验证的前提。这一步的 ROI 高于任何提示词技巧。

---

## 阶段 1 · 需求澄清（先收敛，再动手）

**你说什么**
> 不要写任何代码。针对这个需求，提出 3–5 个最影响设计的问题，并给出每个问题的默认建议。同时列出你认为「明确不做」的范围。

**证据**：一页纸的需求边界：用户是谁、核心场景 3 条、非目标（non-goals）、成功指标、影响面。

**翻车**：AI 直接开始写 → 它已经替你做了 10 个你没同意的设计决策，返工成本远高于提问成本。

关键技巧：**让 AI 主动暴露假设**。
> 在开始前列出你这个方案依赖的全部隐含假设，按「错了会返工」的程度排序。

---

## 阶段 2 · 方案对齐（多方案 + 决策记录）

**你说什么**
> 给我 2–3 个实现方案，每项包含：改动文件清单、对性能/扩展性/安全的影响、迁移与回滚成本、预估工作量。明确推荐哪个、为什么、代价是什么。先不要实现。

在有计划能力的环境里，这一步走**计划模式**：AI 出计划 → 你审批 → 才允许写文件。

**证据**：方案对比表 + 你的一句「采用方案 B，原因是…」。把它写进 `docs/adr/NNN-*.md`。

**翻车**：接受唯一方案。AI 给出的第一个方案通常是「训练分布里最常见的」，不一定是「最适合你的」。多方案对比能把差异暴露出来。

---

## 阶段 3 · 任务拆分（可独立验证的小步）

**你说什么**
> 把这个方案拆成 5–10 个顺序任务，每个任务必须：可单独验证、能单独回滚、说明验证命令或断言。标出依赖关系，指出哪些可以并行。

**证据**：任务列表，每条自带「怎么算完成」。用任务追踪工具维护状态，别用自然记忆。

**翻车**：一个任务 =「实现整个功能」。中间无法验证，出错只能整体重来。

---

## 阶段 4 · 实现（红-绿循环 + 自带证据）

顺序：契约/类型/接口 → 失败测试（红）→ 最小实现（绿）→ 重构 → 集成。

**你说什么**
> 先写会失败的测试并运行给我看失败输出，再实现。完成后运行 `npm run test && npm run typecheck && npm run lint`，把真实输出贴出来。任何一步失败就继续修，不要回来问我「要不要现在测」。

**证据**：真实命令输出（不是复述）；diff 里测试与实现同批出现；覆盖率对关键分支有效。

**翻车**
- AI「先实现后补测试」，测试是照着实现写的 → 只证明代码等于自己。
- AI 修改断言去迁就实现结果。规则：**改测试来放宽行为一律要求人工确认**。
- 「我已完成」但从未运行过任何命令。要求：没贴输出 = 未完成。

UI/前端例外：必须真实运行时验证（浏览器截图 + console + 网络请求），单测通过 ≠ 页面正确。见 [playbook/05-app-types.md](app-types.md)。

---

## 阶段 5 · 独立评审（换一双眼睛）

**你说什么**
> 用三个角色分别审查这次 diff，各自独立输出：① 安全评审员（注入/越权/密钥/依赖）；② 性能工程师（复杂度、N+1、内存与网络放大）；③ 六个月后的接手者（可读性、缺失文档、隐藏耦合）。每条问题给出文件:行号、影响、修复建议、严重级别。

用子智能体/新会话做评审，避免「写代码的上下文」为它自己辩护。

**证据**：问题清单 → 你决定哪些必修哪些记账 → 修复后重跑验证 → 记录。

**翻车**：评审只找出风格问题，因为评审提示太泛。把检查项写死成清单（见 [templates/acceptance-checklist.md](../assets/acceptance-checklist.md)）。

---

## 阶段 6 · 交付与沉淀

**你说什么**
> 生成变更说明：用户视角的 what/why、迁移与回滚步骤、需要运维注意的配置项、验收数据（性能/覆盖率前后对比）。同时列出本次踩到的、值得写进 `AGENTS.md` 的项目级约定。

**证据**：发布记录 + 回滚路径可执行 + 基线文档被更新（这一条最常被跳过，也是复利来源）。

**沉淀判断标准**：凡是「下次会话我还需要再解释一遍」的内容，就该进 `AGENTS.md` 或知识库，而不是留在聊天记录里。

---

## 跨阶段原则

1. **一次一个变更集**。并行改不相干的东西，会让错误定位变成考古。
2. **AI 必须能自主验证**。给它可运行的命令，比给它十句要求更有效。
3. **上下文是稀缺资源**。大范围探索交给只读子智能体，主上下文只收结论 + 文件行号证据。
4. **失败即资产**。同类错误第二次出现，就固化成 lint 规则、CI 检查或文档条款。
5. **人的注意力用在不可替代处**：需求优先级、架构取舍、风险接受、审美判断。其余交给循环。
