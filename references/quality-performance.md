# 03 · 质量与性能

## A. 质量（Quality）

### A1. 把「完成」写成可执行定义

模糊定义无法约束 AI。写死成命令：

```
完成 := 
  <测试命令> 全绿，且新增逻辑有对应新测试
  && <typecheck> 无 error
  && <lint> 无 error
  && <build> 成功且产物体积未超预算
  && 关键用户路径手工/浏览器冒烟通过（截图为证）
  && 受影响文档与 AGENTS.md 已同步
```

给 AI 一条聚合命令（`make check` / `npm run check`），它每次改动后就会自动跑——**验证成本降到 0，AI 才会真的去验证**。

### A2. 测试策略与分工

| 层 | 谁写 | AI 互动要点 |
|---|---|---|
| 单元测试 | AI | 「先写失败测试并展示失败输出」——防止测试跟着实现跑 |
| 契约/集成测试 | AI + 人定关键场景 | 给出 schema/DDL，让它生成参数化用例与边界值 |
| 属性测试(fuzz) | AI | 对解析、序列化、状态机类代码明确要求 property-based |
| E2E | 少而准（人挑路径） | 只覆盖 3–5 条真·黄金路径；多了维护成本反噬 |
| 快照 | 谨慎 | 快照易被无脑更新，等于没有断言 |

**缺陷规程**：每个 bug → 先让 AI 写一个复现它的失败测试（红）→ 再修（绿）→ 提交信息记录根因。这条流程能把回归率压到很低，因为它阻止「改到看起来对了」。

### A3. 静态门槛（不要靠人眼）

类型检查（strict）、lint 规则、格式化工具、依赖漏洞扫描、密钥扫描、schema 迁移检查、覆盖率门槛（对新增代码，而非整体虚高数字）、构建产物体积/包大小基线。

要求 AI：**新增 lint 违规必须为零**；确需抑制规则必须逐条写明理由。

### A4. 评审回路

- 写代码的上下文 ≠ 审代码的上下文（新会话/子智能体）。
- 评审必须输出结构化条目：`文件:行号 | 严重级别 | 影响 | 修复建议`，否则会得到一堆「建议加注释」。
- 人只裁决三件事：业务是否正确、架构是否可接受、风险是否愿承担。风格交给工具。
- 每次评审发现的**项目特有问题** → 固化为规则/检查项，不重复出现。

## B. 性能（Performance）

### B1. 唯一纪律：先测量，再优化，再复测

对 AI 的标准话术：
> 不要提优化建议。先写剖析脚本，跑出当前分布数据（次数、耗时 P50/P95、行数、字节），给我前 3 个瓶颈及其占比。然后只做能解释这些数据的改动，改完复测并给前后对比。

没有基线数字的「优化」几乎总是无效改动 + 新增复杂度。

### B2. 把性能预算写进规格

```
首屏渲染 ≤ 1.5s（P75, 4G）  接口 P95 ≤ 120ms  包体(gzip) ≤ 180KB
单页内存 ≤ 120MB  DB 查询 ≤ 5 次/请求  列表必须分页, 默认 50
```
有了数字，AI 才有优化方向；没有数字，它只能生成「通用最佳实践清单」。

### B3. 强制检查清单（丢给 AI 逐条回答）

**数据层**：N+1 查询、缺失/错位索引、`SELECT *`、无分页全表加载、事务内远程调用、连接池上限与超时缺失。
**计算层**：循环内重复计算/分配、O(n²) 嵌套查找（应换哈希）、同步阻塞点、不必要序列化、正则回溯灾难。
**网络层**：串行请求可并行、重复请求无缓存、无压缩、无边界重试与退避、超时缺失、跨地域往返。
**前端/客户端**：首屏包体积与未做代码分割、长列表未虚拟化、图片未压缩/未懒加载、主线程重复渲染（缺 memo/依赖不当）、布局抖动与强制同步布局、动画未走合成层。
**移动端**：冷启动链路、主线程 I/O、后台定位/刷新耗电、内存泄漏与大图、包体与so/framework体积。

### B4. 缓存的正确姿势

要求 AI 在引入缓存前先回答：一致性容忍窗口多久、失效策略、缓存键基数与内存上限、穿透/雪崩防护、缓存与鉴权边界是否会串数据（多用户共享缓存键是经典越权）。

### B5. 防过早优化

明确告诉 AI：**「可读性优先，只有在数据支撑时才引入复杂优化；任何优化必须留下注释说明它避免了什么具体测量到的问题。」** 否则你会得到充满技巧但没人敢动的代码。

### B6. 性能回归防线

把关键基线做成可重复运行的脚本 + CI 门禁（阈值告警，而非精确值断言，避免抖动误报）。话术：
> 为刚才的优化加一个可重复的性能回归脚本，指标输出到文件，超过基线 20% 时以非零码退出。
