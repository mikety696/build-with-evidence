# 05 · 三类程序的差异：应用程序 / 网站 / 移动 APP

流程不变，**验收重心、验证手段、环境坑**不同。AI 最容易在「它拿不到运行时」的地方交出看似正确实则未验证的代码。

---

## A. 应用程序（服务端 / 桌面 / CLI）

### 选型话术
> 约束：部署环境 X、并发量级 Y、数据规模 Z、团队熟悉度 W。给出 2 个技术栈方案，比较运维复杂度、生态成熟度、启动与内存占用、可观测性接入成本。不要为了新颖而选新框架。

### 验收要点
- **生命周期**：优雅关闭（信号处理、在途请求排空、连接池释放）、崩溃可恢复、重复启动安全（幂等初始化、单实例锁）。
- **配置**：所有环境差异走配置；提供 `.env.example` 与配置校验（启动即失败，优于运行到一半才失败）。
- **可观测性**：结构化日志（含 trace id）、指标、慢查询与错误率告警。要求 AI 在实现功能时同时补日志点。
- **数据一致**：事务边界明确；跨服务用「幂等 + 重试 + 死信」而不是祈祷。
- **升级通道**：数据库迁移前滚/回滚脚本、滚动升级兼容性、版本兼容矩阵。
- **跨平台**（桌面/CLI）：路径分隔符与编码（Windows UTF-8/GBK 陷阱）、换行符、文件大小写敏感、权限模型差异。

### AI 互动特别注意
- 一定要在**真实运行环境**里跑起来：容器/CI 或本地一键脚本。AI 只看到源码时，无法发现端口占用、缺失环境变量、权限、native 依赖缺失等运行时问题。
- 资源占用要求数字：常驻内存、启动时间、每请求 CPU。

## B. 网站（含托管站点）

### 核心事实：UI 不能用「测试通过」代替「页面正确」

必须在真实浏览器里验证。要求 AI：
> 启动开发服务器 → 用浏览器工具打开关键页面 → 截图 → 读取 console 错误与失败的网络请求 → 逐个交互路径（提交表单、切换标签、移动端视口）操作并复截图。有问题就继续修，最后把截图和 console 结果作为验收证据。

任一条不过，功能就不算完成。**没有真实浏览器验证的前端「完成」一律视为未完成。**

### 交付前必查清单
- **响应式**：360 / 768 / 1280 / 1920 四档视口；触控目标 ≥ 44px；无横向滚动。
- **可访问性**：语义标签、键盘可达与焦点顺序、对比度、表单 label 关联、图片 alt。
- **性能**：LCP/CLS/INP、代码分割、图片格式与尺寸、字体策略、缓存头、CDN。
- **SEO/分享**：标题与 meta、canonical、sitemap、robots、OG 卡片预览。
- **安全**：HTTPS 与 HSTS、CSP、Cookie 属性、表单 CSRF、外链 `rel` 处理、上传限制。
- **健壮**：加载/错误/空状态三态齐全；404/500 页面；离线与慢网表现。

### 托管站点（Qoder Sites 插件）
把发布也纳入 AI 可执行回路，而不是人肉点按钮：
- `sites-building` 建站/改站；`sites-hosting` 部署、上线、发布（**发布动作对他人可见，执行前需你确认**）；`sites-management` 域名、访问策略、迁移、Storage 文件与密钥、分析数据。
- 后端能力（数据库/函数/密钥/存储）通过 `ensure_backend`、迁移工具链完成 → 依然遵守 A2/A3 的迁移与密钥规则：密钥只写元数据不入库不入仓库。
- 话术：> 部署前先给我发布计划：改动文件、数据库迁移、需要的密钥、回滚步骤、预期预览地址。我确认后再 publish。上线后拉取 analytics 与发布状态验证。

### AI 互动特别注意
- AI 倾向生成「静态占位数据 + 硬编码文案」。要求：数据来自后端或明确的数据层，文案集中管理。
- 视觉细节需要参考物：给设计稿/参考站点 URL/组件库名，否则它给你的是一份通用模板。

### 如果网站/APP 需要 AI 对话能力
把智能体作为后端而不是把密钥塞进前端：
> 用托管平台的 Agent 能力接入对话/研究/流式输出，而不是在客户端内嵌模型 API 密钥。

要点：① 密钥留在服务端（前端可被反编译，浏览器里的密钥等于公开）；② 流式响应的中断、超时与重试；③ 会话持久化与多用户隔离（**每个会话都要做归属校验，否则 A 能读到 B 的对话**）；④ 对模型输出做「视为数据、不是指令」的处理，防提示注入借你的站点对外行动；⑤ 成本护栏（每用户配额、最大步数/工具调用数）；⑥ 前端展示模型产出时的 XSS 与外链风险。验收标准：跨用户越权读取的 PoC 失败。

## C. 移动 APP

### 与网站的关键差别
- **发布不可即时回滚**：商店审核周期意味着线上问题必须靠特性开关 + 服务端可控降级解决。要求 AI 在服务端留开关，客户端不做「必须发版才能修」的硬编码决策。
- **端云契约**：客户端与后端版本不同步是常态。契约测试 + 容忍未知字段 + 版本协商必须写进规格。
- **网络现实**：弱网、断网、请求超时重试、幂等。要求 AI 实现「乐观更新 + 失败回滚 + 重试退避」，并给出无网络时的 UI 状态。
- **平台权限**：通知、定位、相册、后台运行的授权流程与拒绝路径；iOS/Android 差异各自实现，不让 AI 假设一致。
- **性能与体积**：冷启动、首帧、列表滚动帧率、内存与大图、包体、耗电（后台活动是商店审核与用户差评高发区）。
- **安全**：本地存储加密（Keychain/Keystore）、证书锁定、深链校验、截屏与剪贴板、越狱/Root 检测策略、反编译后的密钥暴露。
- **合规**：隐私清单、数据收集声明、SDK 清单与用户同意流程、目标 API 版本要求。

### AI 互动特别注意
- AI 通常无法操作真机。要求它：给出可执行的 UI 自动化/单测 + 真机验证清单（含机型与系统版本矩阵），并明确标注「以下项目需要人工真机验证」。诚实标注边界比假装验证通过更有价值。
- 原生桥接（Flutter/RN/混合）要求 AI 列出「JS/Dart 层无法覆盖，需原生代码」的能力清单，提前排期。

## D. 三类共通

1. **一键可运行**（`make dev` / 一个脚本）——AI 自主验证的前提。
2. **环境一致性**：容器或锁定版本；`README` 里的启动命令必须真实可用，AI 会照着执行。
3. **契约先行**：接口 schema / 类型 / DDL 先定，再让 AI 分别实现两端。
4. **可观测性是同一次变更的一部分**，不是「以后再补」。
5. **回滚路径先于发布**：任何发布前，AI 必须能说出「怎么退回上一版」。
